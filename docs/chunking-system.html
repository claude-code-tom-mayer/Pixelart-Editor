Architecture

Three levels, one rule

Every entity stands in one or more chunks, depending on its radius. A vertical stack of chunks forms a column, all columns form the map. Each level carries the same two aggregates per team: a bitmask of the groups present, and a plain count of memberships (an entity covering four chunks counts four times).

Columns are the middle level because the two bases face each other along x. "Is there anything hostile ahead of me, or did something slip behind me" is then a walk over column entries rather than over entities — which is exactly what the targeting system asks every time an entity has nobody to fight.

The rule that keeps it cheap: counts are always written through, masks only cascade upwards while they actually change. A removal can never force a rescan of the whole map — it stops at the first level whose value comes out unchanged.

Entities are pure data. There is no node and no object per entity: an entity is an integer id, and every property is one slot in a packed array at that index.

Membership comes in two independent flavours. The coverage chains list an entity in every chunk its radius touches — that is what an area hit walks. The center chain lists it in exactly one chunk, the one its position falls into — that is what a targeting search walks, so an entity spanning six chunks is still scored exactly once.

Aggregation

Add cascades by OR, remove cascades by rebuild

A bitmask grows for free: mask |= groups. It cannot shrink the same way — clearing a bit would be wrong as long as any other entity still holds it. So the two directions are genuinely different operations, and only the add path is O(1) per level.

Every rebuild stops the moment its running OR reaches the old value. They are only ever reached while removing, where a mask can only shrink — so once the partial result matches what was there before, the rest of the scan cannot change it.

Data

Everything is private; some of it is read from outside anyway

Every field carries the _ private prefix the style guide asks for — GDScript cannot enforce access control across classes, so _ here means "the index's own bookkeeping," not "nobody else may touch it." G_HitServer and G_TargetingServer read a handful of these arrays directly (G_ChunkingServer._entityPosition[id] and the like), which keeps a function call out of every inner loop. Writing to one of these from outside skips the chunk update and corrupts the grid — see Rules.

Each per team aggregate is a single packed array where the team selects a block and the chunk or column selects the slot, so adding a third team means adding one enum entry and nothing else.

Every row below opens. Closed, it reads like a table; open, it explains the field with real values from the example world, and draws it where a picture helps.

The example world — three entities on a 4 × 3 grid. Every example on this page uses it.

A shrunk grid, so every array fits on screen: CHUNK_SIZE = 128, 4 columns × 3 rows, CHUNK_COUNT = 12, MAP_SIZE = 512 × 384. The shipped default is 32 × 32; nothing else changes. Two groups are defined by the game: GROUND = 1 << 0 (0b01) and AIR = 1 << 1 (0b10). The entities were registered in id order.

Per entity data, read directly by the servers built on top

FieldTypeHolds
_entityTeamPackedByteArrayTeam, as a TEAM value

One byte per id: 0 = ATTACKER, 1 = DEFENDER. It does two jobs — it answers "is this an opponent?" for every hit and every search, and it picks which team block of the aggregate arrays an add or remove writes into.

Fixed at registration; there is no setter. An entity that changes sides has to be unregistered and registered again.

_entityGroupsPackedInt64ArrayBitmask of the groups the entity belongs to

What the entity is, as up to 64 bits whose meaning the game defines. The index never interprets a bit — it only ORs them into the chunk, column and map masks so a search can ask "is there any AIR here?" without opening a chunk.

An entity can be several things at once: a flying mount carrying a rider could be GROUND | AIR = 0b11. Like the team it is set once, in register_entity(); the masks it was ORed into could not be updated otherwise.

_entityPositionPackedVector2ArrayCurrent position, in world units

The chunk a position falls into is floor(position / CHUNK_SIZE) per axis, clamped to the grid:

id 2 at (256, 128): column = floor(256 / 128) = 2 row = floor(128 / 128) = 1 chunk = row * MAP_CHUNK_COLUMNS + column = 1 * 4 + 2 = 6

A position exactly on a border belongs to the chunk right of / below it. Positions outside the map clamp into the border chunks instead of erroring. Only write it through set_position() — writing the array directly leaves every chunk list, count and mask describing the old position.

_entityRadiusPackedFloat32ArrayEffect radius — what decides chunk coverage

The index turns position ± radius into a square and lists the entity in every chunk that square touches:

id 2: square (256-40, 128-40) … (256+40, 128+40) = (216, 88) … (296, 168) columns floor(216/128) … floor(296/128) = 1 … 2 rows floor( 88/128) … floor(168/128) = 0 … 1 → chunks 1, 2, 5, 6

A square, not a circle, on purpose: it can list an entity in a corner chunk its circle does not quite reach, but it can never miss one. The hit server treats this value as the full silhouette radius (scaled by its radius curve, if any); targeting adds it to the attacker's hit range.

_entityPreUnregisteredPackedByteArray1 while announced for removal but still in the grid

Set by pre_unregister_entity(). The entity stays in every chunk, keeps counting and can still move and hit — but the hit server skips it as a target and the targeting server never picks it, and drops everyone already aiming at it. Typical use: a unit starts its death animation. It should still take up space for half a second, but nothing should waste an attack on it.

Skipping it is optional: unregister_entity() works on an entity that was never announced.

_entityUnregisteringPackedByteArray1 while removed but the id is still locked

Set by unregister_entity(), cleared by release_removed_ids() (see the timeline above). While it is 1 the entity is out of every chunk, but its id cannot be handed out again yet.

Why the lock: say id 1 dies mid-frame while an explosion is still queued to hit id 1 later in the same frame. If the id were free at once, a new entity spawned in between would get id 1 and eat the damage. With the lock, the old id 1 is simply skipped (hit and targeting both check this flag) until the end of the frame.

It also makes removal idempotent: a second unregister_entity(1) sees the 1 and returns, so id 1 cannot land in the free list twice.

_entityChunkAreaArray[Vector4i]Covered rectangle as (minColumn, minRow, maxColumn, maxRow)

The last coverage rectangle, kept so a move can be compared against it. If the new rectangle is identical, set_position() leaves every chunk alone — the fast path.

Moving id 2 by 20 units to (276, 128) gives the square 236 … 316 — still columns 1 … 2 — so the rectangle is unchanged and nothing happens. Moving it to (300, 128) changes the rectangle to (2, 0, 2, 1): only the slots in chunks 1 and 5 are unlinked, 2 and 6 are not touched. Array[Vector4i] because Godot has no packed Vector4i array.

_entityCenterColumn · _entityCenterRowPackedInt32ArrayColumn and row of the entity's center chunk — what search reads

The same chunk as _entityCenterChunk, pre-split into column and row. Targeting measures chunk distances between two entities thousands of times per search; reading two ints saves a % and a / each time. Written only when the center chunk actually changes.

Coverage membership — one slot per chunk an entity touches

An intrusive doubly linked list, threaded two ways through the same slot array: once per chunk, once per entity. No list is ever copied to add or remove a member.

How the two chains share one slot array — drawn for the example world

A slot is one "entity X stands in chunk Y" fact. The example world has six of them: id 0 in chunk 0, id 1 in chunk 6, and id 2 in chunks 1, 2, 5 and 6. Each slot is one index across six parallel arrays:

## Who stands in chunk 6? slot = _chunkHead[6] # 5 → _slotEntity[5] = id 2 slot = _slotChunkNext[5] # 1 → _slotEntity[1] = id 1 slot = _slotChunkNext[1] # −1 → done: ids 2, 1 ## Where does entity 2 stand? slot = _entitySlotHead[2] # 5 → chunk 6, then 4 → chunk 5, 3 → chunk 2, 2 → chunk 1, −1

Removing one slot, e.g. slot 4 when id 2 leaves chunk 5: in chunk 5's chain its prev is −1, so _chunkHead[5] = −1. In id 2's chain its prev is 5 and its next is 3, so _slotEntityNext[5] = 3 and _slotEntityPrev[3] = 5. Slot 4 goes to _freeSlots. Four writes, whatever the chunk holds.

FieldTypeHolds
_chunkHeadPackedInt32ArrayFirst slot of each chunk's chain, or NO_SLOT

One entry per chunk. The entry to start from when you want everything standing in a chunk; −1 means the chunk is empty.

slot = _chunkHead[c] while slot != NO_SLOT: id = _slotEntity[slot] # use id slot = _slotChunkNext[slot]

The hit server walks exactly this loop over the chunks under a hit shape.

_entitySlotHeadPackedInt32ArrayFirst slot of each entity's own chain, or NO_SLOT

One entry per entity id. Following it lists every chunk the entity stands in (for id 2: slots 5, 4, 3, 2 → chunks 6, 5, 2, 1). unregister_entity() and a move that changes the rectangle walk this chain to find the slots to unlink, instead of searching every chunk.

_slotEntity · _slotChunkPackedInt32ArrayThe entity and the chunk one slot belongs to

The payload of a slot. A chunk walk reads _slotEntity to get an id; an entity walk reads _slotChunk to get a chunk. On removal, _slotChunk says which chunk's counts and masks to update.

_slotChunkNext · _slotChunkPrevPackedInt32ArrayNeighbours of a slot inside its chunk's chain

Chunk 6 holds slots 5 and 1: next[5] = 1, prev[1] = 5. −1 marks the ends. Prev is only there so removal needs no search: to unlink slot 1 you already know its neighbour is 5.

_slotEntityNext · _slotEntityPrevPackedInt32ArrayNeighbours of a slot inside its entity's chain

The same idea, threaded per entity. Entity 2's chain is 5 → 4 → 3 → 2. Entities 0 and 1 stand in one chunk each, so their only slot has −1 on both sides.

_freeSlotsPackedInt32ArrayMembership slots ready to be handed out again

A stack of unlinked slot indices. After id 2 moves to (300, 128) it leaves chunks 1 and 5, so slots 2 and 4 are pushed:

The next membership pops the last one (2) instead of growing six arrays. The slot arrays therefore never shrink: their length is the most memberships that ever existed at once, and a freed slot keeps stale values until it is reused.

Center membership — exactly one slot per entity

A second, unrelated chain: every entity sits in exactly one chunk here, the one its position falls into. This is what lets a search visit each entity once no matter how many chunks its radius covers.

FieldTypeHolds
_entityCenterChunkPackedInt32ArrayThe chunk an entity's center link sits in, or NO_COLUMN

Compared on every set_position(): if the position still falls into the same chunk, the center chain is not touched. −1 (it reuses NO_COLUMN as its "nowhere" value) while the entity is not linked — before its first placement and after it was unregistered.

_centerHeadPackedInt32ArrayFirst entity of a chunk's center chain, or NO_ENTITY

Unlike the coverage chains, this one needs no slot array: an entity has exactly one center, so the links live directly on the entity id. Chunks 1, 2 and 5 are covered by id 2 but hold no center — a search opening them finds nothing, and so never scores id 2 four times.

_centerNext · _centerPrevPackedInt32ArrayNeighbours of an entity inside the center chain of its chunk

Id 1 was placed first, id 2 was pushed in front of it. Walk it with id = _centerHead[c]; while id != NO_ENTITY: … id = _centerNext[id] — the loop targeting's _scan_chunk() runs.

Per team, per chunk / column / map aggregates

Each is one flat array made of team blocks: the team picks the block, the chunk or column picks the slot inside it.

FieldTypeHolds
_chunkGroupsPackedInt64ArrayOR of the groups of every entity of a team standing in a chunk

Size TEAM_COUNT × CHUNK_COUNT; index team * CHUNK_COUNT + chunk. Defender chunk 6 is index 1 × 12 + 6 = 18; it holds id 1 (GROUND) and id 2 (AIR), so its mask is 0b01 | 0b10 = 0b11.

Adding just ORs in (0b10 | 0b01). Removing cannot "un-OR" a bit someone else may still hold, so it rebuilds from what is left — see the cascade.

_columnGroupsPackedInt64ArrayOR of the chunk masks of one column, per team

Size TEAM_COUNT × MAP_CHUNK_COLUMNS; index team * MAP_CHUNK_COLUMNS + column.

Lets a search skip a whole column with one lookup: an attacker looking for AIR checks _columnGroups[1*4 + 3] & 0b10, sees 0, and never opens chunks 3, 7 or 11. Columns (not rows) because the two bases face each other along x.

_mapGroupsPackedInt64ArrayOR of all column masks, per team

One entry per team: "does this team have any AIR at all?" If a search's groups are not in here, it returns before touching a single chunk.

_chunkCounts · _columnCounts · _mapCountsPackedInt32ArrayMemberships per team and level — not distinct entities

Same team-block layout as the masks, but a plain number. It counts slots, not entities: id 2 stands in four chunks, so it adds 1 to four chunk counts, and so 4 to the map count.

The defenders are two entities but _mapCounts[DEFENDER] = 5 (1 slot of id 1 + 4 of id 2). That is fine for what the counts are used for — "is anybody of that team here, yes or no" (> 0) and noticing a column running empty — but don't read them as head counts. Counts ignore groups, so they include invisible entities too.

_teamMinColumn · _teamMaxColumnPackedInt32ArrayOutermost occupied column per team, or NO_COLUMN

An attacker in column 2 asks "did a defender slip behind me?" → has_opponent_before_column(2, ATTACKER) reads _teamMinColumn[DEFENDER] = 1 < 2 → yes. One read per team, however wide the map.

Kept current from the column counts: when a column goes from 0 to 1 member, the span may widen; when it goes to 0 and it was the edge, the edge is walked inwards to the next non-empty column. If id 2 moved right out of column 1, the defender minimum would step from 1 to 2. −1 on both while a team holds nothing.

Free lists

FieldTypeHolds
_pendingFreeIdsPackedInt32ArrayIds removed since the last release_removed_ids()

The waiting room between "removed" and "reusable" (the locked phase in the _entityPreUnregistered timeline above).

frame 10 unregister_entity(1) _pendingFreeIds = [1] _freeIds = [] frame 10 release_removed_ids() _pendingFreeIds = [] _freeIds = [1] # s_entityReleased(1) frame 11 register_entity(…) returns 1 _freeIds = []
_freeIdsPackedInt32ArrayIds ready to be handed out again

A stack: register_entity() pops the most recently freed id. Only when it is empty does a brand-new id get appended to every per-entity array — and only then is s_entitySlotAppended emitted, so the other servers grow along. The id space therefore never shrinks; it is as large as the most entities alive at once.

Both membership lists are doubly linked, so unlinking a slot or a center entry is a fixed number of index rewrites — no swap, no search, and no per entity index to keep in step. _teamMinColumn/_teamMaxColumn only rescan when the column that just emptied was the span edge, so the amortised cost stays near zero. The UPPER_CASE members at the top of G_ChunkingServer are cached copies of the C_ChunkingServer values, per the style guide's caching rule.

Movement

The rectangle check that skips the work

set_position() and set_radius() both go through one internal step that compares the new chunk rectangle against the one the entity already covers, and skips the coverage update entirely when they match. _compute_chunk_area() is allocation free — it returns a Vector4i, a value type — so the fast path costs four clamps and one comparison.

set_position() also updates the entity's center chunk, through the same kind of drop-out: _apply_center_chunk() returns at once when the position did not cross into a new chunk. The two checks are independent — a small move can shift the center chunk without changing the coverage rectangle, or the reverse for a large entity moving near its own edge.

The coverage fast path is taken on the large majority of movement calls, which is why nothing else in the system is allowed to add work to it.

Reference

C_ChunkingServer

Configuration is four constants; the grid the server actually uses is derived from them once, in _static_init(), on class load. They are static var rather than const because GDScript cannot call ceili() or maxi() in a constant expression.

NameKindMeaning
CONFIGURED_MAP_SIZEconst Vector2World size the grid has to cover

Default (4096, 4096), in world units. The grid actually built (MAP_SIZE) is at least this large; it only grows when square chunks don't divide it evenly (see the table below).

CONFIGURED_CHUNK_COLUMNS / _ROWSconst intWanted counts — a wish, not a guarantee

Default 32 × 32. Kept exactly only if map width / columns equals map height / rows; otherwise the average of both edges becomes the chunk edge and the counts are derived back from it. Smaller chunks mean tighter hit and search areas but more chunks to walk; bigger chunks the reverse.

COVERAGE_EPSILONconst floatTolerance so float error cannot add a spurious column

0.0001. The column count is ceil(map width / CHUNK_SIZE). If rounding makes that division come out as 32.0000001 instead of 32, ceil gives 33 — a whole extra column that covers nothing. Subtracting the epsilon first gives ceil(31.9999…) = 32.

TEAMenumATTACKER, DEFENDER — the values index every per-team container

ATTACKER = 0, DEFENDER = 1. These numbers are array indices: _mapGroups[TEAM.DEFENDER], TEAM_BASE_X[team]. A third team needs one more enum entry here — and one more entry in each TEAM_* array of C_TargetingServer, which asserts that the sizes match.

NO_COLUMN · NO_SLOT · NO_ENTITYconst int"Points nowhere" markers, all −1

All three are −1; the name says which kind of index is missing, so a comparison reads as what it means:

  • NO_SLOT — end of a coverage chain, or an empty _chunkHead / _entitySlotHead.
  • NO_ENTITY — end of a center chain, or an empty _centerHead.
  • NO_COLUMN — _teamMinColumn / _teamMaxColumn of a team holding nothing, and _entityCenterChunk of an entity that is not linked anywhere.
CHUNK_SIZEstatic floatChunk edge, identical on both axes

Default 128 (4096 / 32). Every position to chunk conversion divides by it: column = floor(x / CHUNK_SIZE).

MAP_CHUNK_COLUMNS / _ROWSstatic intCounts after the square recalculation

Default 32 × 32. Chunk ids run row by row, so chunk = row * MAP_CHUNK_COLUMNS + column, and going down one row inside a column means adding MAP_CHUNK_COLUMNS. In the 4 × 3 example world: row 1, column 2 → 1 * 4 + 2 = 6.

CHUNK_COUNT · MAP_SIZE · TEAM_COUNTstaticTotals derived from the above

Default CHUNK_COUNT = 1024, MAP_SIZE = (4096, 4096), TEAM_COUNT = 2. CHUNK_COUNT is the length of one team block in the per-chunk aggregates; TEAM_COUNT is the number of blocks. MAP_SIZE is what the grid really covers; targeting pins the defender base to MAP_SIZE.x.

Square chunks, whatever you configure

A column count and a row count imply two different chunk edges. If they disagree, chunks are rectangles. The recalculation takes the edge closest to both wishes, uses it on both axes, and derives the counts back from it so the grid still covers the whole map:

CHUNK_SIZE = (MAP_SIZE.x / COLUMNS + MAP_SIZE.y / ROWS) * 0.5 MAP_CHUNK_COLUMNS = ceil(CONFIGURED_MAP_SIZE.x / CHUNK_SIZE) MAP_CHUNK_ROWS = ceil(CONFIGURED_MAP_SIZE.y / CHUNK_SIZE)

Contract

What the caller has to respect

  • The per entity arrays are read only for everyone but the index. Writing _entityPosition directly skips the chunk update and corrupts the grid — go through set_position().
  • release_removed_ids() once per frame, last. It is the only thing that recycles ids, and the lock it releases is what makes a queued damage event safe.
  • An unregistered id is dead until re-registered. The index does not re-check a caller's id.
  • 64 groups maximum. Groups are bits in an int64; their meaning is the caller's to define.
  • Teams are array indices. Pass TEAM values; a third team needs only a new enum entry.
  • The grid is fixed after class load. Changing the configuration means changing the constants and restarting.
Measurements

Where the cost went

Both optimisations were measured before being written, on a transliteration of the algorithm rather than in Godot — so the iteration counts are exact and the wall-clock gain is not. They are reported as ratios for that reason. The movement fast path is in the table above; this is the other one.

Correctness

Fuzz-tested against a brute-force rebuild: 50 trials × 500 random operations mixing registration, long moves, sub-chunk nudges, radius changes, removal and release. After each batch every chunk and column mask, every count at all three levels, the coverage and center membership chains, the cached rectangle and the id lifecycle are compared against a full recomputation. All pass.

That validated the algorithm, ahead of the GDScript. The end-to-end suite in res://Tests/EndToEndTest.gd now runs this and the two servers built on it inside Godot itself.
