Overview

Targets are lost, not polled

The expensive part of targeting is deciding when to search. This server never re-validates a target per tick. A target is dropped by exactly three events: it gets announced for removal, it turns invisible to someone who cannot see invisibles, or somebody calls drop_targeters() on it. Everything else — running out of range, running across the map — keeps the target.

That makes a targeting entity cost a handful of comparisons per tick, and it makes searching rare enough that the search itself can be generous: the whole chunk square around the entity, scanned once.

The server produces exactly one thing for the outside world: get_target_position(), the point movement should head for. It never moves anything itself.

Behaviour

Four states, and why marching is not one

Dropped

There is no MARCH state. A marching state ranked above searching would let an entity walk clean through an enemy line without ever looking up. Marching is what SEARCH returns, so an entity keeps scanning every tick while it advances and picks up a target the moment one comes into range.

Flee

A fleeing entity drops its own target and runs. It keeps fleeing while a targeter is inside its flee distance and it has not reached its own base x. Reaching the base ends the flight even if the threat is still chasing, so nothing runs forever.

Behind

Before advancing, an entity checks the columns behind it. That check reads column counts, which include invisible entities — so something that sneaked past is noticed even by an entity that cannot see it, and the entity falls back instead of marching on.

Simplification

Ranges are chunk counts, not metres

Search and flee distances are counted in chunks, not world units. A search covers the square of chunks around the entity instead of a circle, and a diagonal step costs DIAGONAL_CHUNK_COST rather than a square root. Nothing in the search or the scoring touches real geometry.

Only one distance stays real: the hit range that separates APPROACH from COMBAT. Quantising that one to chunks would let a unit open fire from anywhere in a neighbouring chunk, which reads as sloppy in play. It is stored squared, so that test is a subtraction and a multiply.

DistanceUnitUsed for
searchChunkschunksHow far the scan square reaches in each direction

The entity's own chunk comes from the rectangle the index already maintains — no extra cache, and no cost added to the movement path, which is the hottest code in the whole system.

Search

One walk, two winners

An entity can name priority groups it would rather go after. Conceptually that is two searches: one for the preferred groups, then one for the normal ones. In practice it is a single walk with two best-trackers — every candidate is scored once and lands in whichever pool it belongs to. If the priority pool has anything in it at the end, it wins. Same result, half the work.

  1. 1

    Map check. If no opposing team holds any of the searched groups anywhere, the search returns immediately — one bitwise AND per team, before a single chunk is touched.

  2. 2

    Chunk square. The entity's own chunk rectangle, grown by searchChunks in each direction and clamped to the map.

  3. 3

    Skip empty chunks. has_opponent_in_chunk() rejects a whole chunk on a count lookup.

  4. 4

    Filter, then score. Team, removal flags, group mask and invisibility first; only survivors get weighed.

  5. 5

    Best priority, else best normal. No duplicate guard is needed — an entity spanning several chunks scores identically each time, and only the maximum is kept.

Scoring

Five terms, no geometry

Every term is a comparison, a bit test or an array size. The weights live in C_TargetingServer and are meant to be tuned there.

WeightApplies whenRead from
WEIGHT_CLOSENESSPer chunk nearer than the edge of the search squareChunk coordinates
WEIGHT_FOCUSThe candidate carries focus and the searcher does not ignore itTwo flag bits
WEIGHT_BEHINDThe candidate sits behind the searcher's march directionColumn comparison
WEIGHT_CROWDINGSubtracted once per entity already targeting the candidate_targetersOf[id].size()
WEIGHT_MUTUALThe candidate already targets the searcherOne array read

The crowding term makes the outcome depend on the order entities search in — the first to pick gets the uncrowded target. That is fine for singleplayer; it would need pinning down for replays or lockstep.

Data

The link that goes both ways

Three things need to know who targets whom: the crowding term, the flee check, and releasing a dying entity's pursuers. All three are cheap because the link is stored from both ends.

FieldTypeHolds
_entityTargetPackedInt32ArrayWho this entity targets, or NO_TARGET
_targetersOfArray[PackedInt32Array]Everyone targeting this entity
_entityTargeterIndexPackedInt32ArrayOwn slot inside the target's list — what makes unlinking O(1)
_entityFlagsPackedByteArrayInvisible, sees invisible, has focus, ignores focus — four bits, one lookup

Unlinking swaps the last targeter into the freed slot and repairs its index, exactly like the chunk lists. The size of _targetersOf[id] is the crowding count, so there is no counter that can drift out of step.

Reference

Public API

Entities call it directly with the id the chunk index gave them. Everything is set at registration through register(p_id, p_targetingData); the setters are for changes during a round. Removal needs no call here — the server follows the entity_pre_unregistered, entity_unregistered and entity_released signals of the index.

update_entitypublicO(targeters)
func update_entity(p_id: int) -> int

The per tick step: flee check, range check, state. Never searches. Returns the new STATE.

search_targetpublicO(entities in the square)
func search_target(p_id: int) -> int

The scan, triggered by the entity so the work can be spread across ticks. Assigns the winner and returns it, or NO_TARGET.

get_target_positionpublicO(columns) worst case
func get_target_position(p_id: int) -> Vector2

Fighting and approaching return the target's own position. Fleeing returns the entity's own base x at its current y. Searching returns the enemy base x — or its own, if something is behind it or the map holds nothing it may go after.

drop_targeterspublicO(targeters)
func drop_targeters(p_id: int) -> void

The manual third way to lose a target. Everyone aiming here goes back to SEARCH.

Contract

What the caller has to respect

  • Only three events lose a target. Pre-unregistration, turning invisible to a blind searcher, and drop_targeters(). Nothing polls.
  • The entity triggers its own search. update_entity() never does — that split is what lets searches be spread over ticks later.
  • Movement is not in here. The server reports a position; something else has to walk towards it.
  • Base and march x are fixed per team in C_TargetingServer. Attackers hold the left of the map, defenders the right.
  • Pre-unregistered entities are never targeted, and neither are invisible ones unless the searcher carries FLAG_TARGETS_INVISIBLE.
  • get_targeters() hands out live state. Read it, do not store it, do not write to it.

Verification

The link graph was fuzz-tested against its invariants: 40 worlds × 400 random assign, drop, hide, announce, remove and release operations, asserting that every back reference resolves, every targeter index matches its slot, nobody targets their own team or a removed entity, and that a reachable priority candidate is never passed over. All pass.

That validates the algorithm, not the GDScript — none of it has been through the Godot parser yet.
