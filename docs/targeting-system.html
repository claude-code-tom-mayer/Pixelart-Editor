Overview

Targets are lost, not polled

The expensive part of targeting is deciding when to search. This server never re-validates a target per tick. A target is dropped by exactly three events: it gets announced for removal, it turns invisible to someone who cannot see invisibles, or somebody calls drop_targeters() on it. Everything else — running out of range, running across the map — keeps the target.

That makes a targeting entity cost a handful of comparisons per tick, and it makes searching rare enough that the search itself can be generous: the whole chunk square around the entity, scanned once.

The server produces exactly one thing for the outside world: get_target_position(), the point movement should head for. It never moves anything itself.

Behaviour

Four states, and why marching is not one

Dropped

There is no MARCH state. A marching state ranked above searching would let an entity walk clean through an enemy line without ever looking up. Marching is what SEARCH returns, so an entity keeps scanning every tick while it advances and picks up a target the moment one comes into range.

Flee

A fleeing entity drops its own target and runs. It keeps fleeing while a targeter is inside its flee distance and it has not reached its own base x. Reaching the base ends the flight even if the threat is still chasing, so nothing runs forever.

Behind

Before advancing, an entity checks the columns behind it. has_opponent_before/after_column() reads the outermost occupied column of the opposing team — itself kept current from raw counts, which include invisible entities — so something that sneaked past is noticed even by an entity that cannot see it, and the entity falls back instead of marching on.

Simplification

Ranges are chunk counts, not metres

Search and flee distances are counted in chunks, not world units. A search covers the square of chunks around the entity instead of a circle, and a diagonal step costs DIAGONAL_CHUNK_COST rather than a square root. Nothing in the search or the scoring touches real geometry.

"The entity's own chunk" is not the coverage rectangle the index maintains for hits — it is a separate center chunk, the single chunk the entity's position falls into (G_ChunkingServer._entityCenterColumn/_entityCenterRow). The index keeps it current on every set_position() call, through its own drop-out check, so reading it here is a plain array lookup.

Only one distance stays real: the hit range that separates APPROACH from COMBAT. Quantising that one to chunks would let a unit open fire from anywhere in a neighbouring chunk, which reads as sloppy in play. It is stored as a plain distance — the target's radius is added on top fresh at check time, since it differs per opponent — and only that sum is squared, so the test itself is one addition, one multiply and one compare.

DistanceUnit · defaultUsed for
searchChunkschunks · 4How far the scan square reaches in each direction

Stored per entity as _entitySearchChunks. With 2, the search covers the 5 × 5 chunks around the searcher's center chunk (ring 0, 1 and 2), clamped to the map. With the default 4 it is 9 × 9 = 81 chunks, 1152 × 1152 world units on the default grid.

Rings are scanned from the inside out, so the search can stop early once no outer ring can win (see Scoring). A candidate is found by its center chunk: a big enemy whose body reaches into the square but whose center is outside it is not found.

fleeChunkschunks · 2How close a targeter has to be to start a flight

Stored as _entityFleeChunks. Every tick, update_entity() measures the chunk distance to each entity that targets this one; if any is ≤ fleeChunks, it drops its own target and flees. In the drawing above, a targeter standing on any bold orange cell triggers it.

  • 0 — flees only from a targeter in its own center chunk.
  • −1 — never flees (no distance is below 0).
  • The default 2 means every entity flees once targeted from nearby. Set −1 in the R_TargetingData of units that should stand and fight.

Flight ends once the entity is within BASE_REACHED_EPSILON (32 units) of its own base x.

hitRangeworld units · 64The real distance at which combat begins

Stored as _entityHitRange. Measured to the target's edge, so the target's radius is added at check time:

hitRange 64, target radius 20 → reach = 84, reach² = 7056 distance 80: 80² = 6400 ≤ 7056 → COMBAT distance 90: 90² = 8100 > 7056 → APPROACH

A spearman might use 40, an archer 400. Whether the attack then really lands is the hit server's decision — this only switches the state.

The entity's own chunk is its center chunk, kept current by the index on every move — no cost added to the movement path, which is the hottest code in the whole system.

Search

One walk, two winners, each entity seen once

An entity can name priority groups it would rather go after. Conceptually that is two searches: one for the preferred groups, then one for the normal ones. In practice it is a single walk with two best-trackers — every candidate is scored once and lands in whichever pool it belongs to. If the priority pool has anything in it at the end, it wins. Same result, half the work.

  1. 1

    Map check. If no opposing team holds any of the searched groups anywhere, the search returns immediately — one bitwise AND per team, before a single chunk is touched.

  2. 2

    Chunk square, ring by ring. The entity's own center chunk, grown by searchChunks in each direction and clamped to the map, scanned ring by ring from distance 0 outwards.

  3. 3

    Skip empty columns and chunks. column_has_opponent_group() and chunk_has_opponent_group() reject a whole column or chunk on a mask lookup, before any candidate inside it is read.

  4. 4

    Walk the center chain, filter, then score. A chunk's candidates are its center members only — G_ChunkingServer._centerHead/_centerNext — so an entity spanning several chunks is offered exactly once, never rescored, never guarded against. Team, removal flags, group mask and invisibility are checked first; only survivors get weighed.

  5. 5

    Best priority, else best normal. Kept across rings; the lower id wins a tied score, so the result cannot depend on chunk iteration order.

  6. 6

    Stop once no further ring can win. A chunk at ring r is at least r steps away, so its best possible closeness score is fixed. Once that upper bound — closeness plus every bonus a candidate could still add — cannot beat what the search already holds, the remaining rings are skipped.

Scoring

Five terms, no geometry

Every term is a comparison, a bit test or an array size. The weights live in C_TargetingServer and are meant to be tuned there.

Worked example: three candidates, one winner — and when the search may stop early

An attacker (marches towards larger x) stands in column 5, row 5 with searchChunks = 4. It does not ignore focus. Three defenders are in range:

CandidateClosenessFocusBehindMutualCrowdingScore
A at (7, 6)4 − 2.45 = 1.55———2 × −1.5−1.45
B at (4, 5)4 − 1 = 3—+3+4—10
C at (8, 5)4 − 3 = 1+6——1 × −1.55.5

B is one column behind ((4 − 5) × +1 < 0) and already attacks the searcher — two strong reasons to turn around. C is a focus target but already has one pursuer. A is far and crowded.

Early stop. Before scanning ring r, the best score anything out there could still reach is (searchChunks − r) × WEIGHT_CLOSENESS + every bonus, crowding left out because it only subtracts. Here every bonus is 3 + 4 + 6 = 13, so before ring 2 the bound is 2 + 13 = 15. B's 10 cannot rule that out, so the search runs to the end. A candidate scoring 17 in ring 0 (closeness 4 + all three bonuses) would beat the ring 1 bound of 16 and end the search right there. With these weights, the early stop mostly fires when a strong candidate is very close.

WeightValueApplies when
WEIGHT_CLOSENESS1.0 per chunkPer chunk nearer than the edge of the search square

(searchChunks − chunk distance) × 1.0. With reach 4: 4 in the searcher's own chunk, 3 next door, 1.1 two diagonals away (4 − 2.9), 0 four chunks straight out, and even negative in the far corners (4 − 4 × 1.45 = −1.8). It is the only term that depends on distance, and it is what makes the other terms "tie breakers with weight".

WEIGHT_FOCUS+6.0The candidate carries focus and the searcher does not ignore it

Worth six chunks of closeness: a focus target six chunks further away ties with a plain one right next door. Candidate flag FLAG_HAS_FOCUS set and searcher flag FLAG_IGNORES_FOCUS clear.

WEIGHT_BEHIND+3.0The candidate sits behind the searcher's march direction

Decided by columns only: (candidate column − searcher column) × TEAM_FORWARD_SIGN < 0. For an attacker (sign +1) that is any column left of its own; for a defender (sign −1), any column right of it. The same column is not "behind".

WEIGHT_CROWDING−1.5 eachSubtracted once per entity already targeting the candidate

Read as _targetersOf[candidate].size(). Spreads attackers out: a target already chased by four loses 6 points, as much as a focus bonus. Because it depends on who searched earlier, the result depends on search order (see note below).

WEIGHT_MUTUAL+4.0The candidate already targets the searcher

_entityTarget[candidate] == searcher. "Fight whoever is fighting you" — keeps duels stable instead of two units chasing third parties past each other.

The crowding term makes the outcome depend on the order entities search in — the first to pick gets the uncrowded target. That is fine for singleplayer; it would need pinning down for replays or lockstep.

Data

The link that goes both ways

Three things need to know who targets whom: the crowding term, the flee check, and releasing a dying entity's pursuers. All three are cheap because the link is stored from both ends.

FieldTypeHolds
_entityTargetPackedInt32ArrayWho this entity targets, or NO_TARGET

The forward link. Three attackers 4, 9 and 12 all target defender 20:

Changes only through search_target() (assign) and the three drop events. get_target() reads it.

_targetersOfArray[PackedInt32Array]Everyone targeting this entity — its size is the crowding count

The backward link. Used by the crowding term (its size), the flee check (walk it, measure each), and every drop event (walk it, drop each). Unordered: dropping reorders it.

_entityTargeterIndexPackedInt32ArrayOwn slot inside the target's list — what makes unlinking O(1)

Without it, id 4 dropping its target would have to search 20's list. With it, the drop is a swap-and-pop: move the last entry into the hole, shrink by one, fix the moved entry's index.

slot = _entityTargeterIndex[4] # 0 list[0] = list[last] # 12 moves into the hole list.resize(last) # [12, 9] _entityTargeterIndex[12] = 0 # 12 learns its new slot _entityTarget[4] = NO_TARGET; _entityState[4] = SEARCH

Unlinking swaps the last targeter into the freed slot and repairs its index — a swap-and-pop on a packed array, unlike the doubly linked chunk lists. The size of _targetersOf[id] is the crowding count, so there is no counter that can drift out of step.

Data

What the targeting server stores

Per entity packed arrays indexed by id, like the other two servers — most filled once from R_TargetingData at register(). Positions, teams, groups and center chunks are read from G_ChunkingServer, never copied. The _search* members hold the one search that is running.

Per entity

FieldTypeHolds
_entityTargetedGroupsPackedInt64ArrayGroups the entity may go after

Matched against candidates' _entityGroups in the chunk index, so it uses the same bits. With GROUND = 0b01, AIR = 0b10: a swordsman 0b01, an archer 0b11, an anti-air tower 0b10. 0 means it never finds anything.

_entityPriorityTargetedGroupsPackedInt64ArrayGroups it goes after before considering the normal ones

An archer with targeted 0b11 and priority 0b10: if any AIR enemy is in its square, it takes the best-scoring one of those, even if a ground unit scores far higher. Reference

Public API

Entities call it directly with the id the chunk index gave them. Everything is set at registration through register(p_id, p_targetingData); the setters are for changes during a round. Removal needs no call here — the server follows the s_entityPreUnregistered, s_entityUnregistered and s_entityReleased signals of the index.

update_entitypublicO(targeters)
func update_entity(p_id: int) -> int

The per tick step: flee check, range check, state. Never searches. Returns the new STATE.

search_targetpublicO(entities in the square)
func search_target(p_id: int) -> int

The scan, triggered by the entity so the work can be spread across ticks. Assigns the winner and returns it, or NO_TARGET.

get_target_positionpublicO(1)
func get_target_position(p_id: int) -> Vector2

Fighting and approaching return the target's own position. Fleeing returns the entity's own base x at its current y. Searching returns the enemy base x — or its own, if has_opponent_before/after_column() says something is behind it, or the map holds nothing it may go after.

drop_targeterspublicO(targeters)
func drop_targeters(p_id: int) -> void

The manual third way to lose a target. Everyone aiming here goes back to SEARCH.

Contract

What the caller has to respect

  • Only three events lose a target. Pre-unregistration, turning invisible to a blind searcher, and drop_targeters(). Nothing polls.
  • The entity triggers its own search. update_entity() never does — that split is what lets searches be spread over ticks later.
  • Movement is not in here. The server reports a position; something else has to walk towards it.
  • Base and march x are fixed per team in C_TargetingServer. Attackers hold the left of the map, defenders the right.
  • Pre-unregistered entities are never targeted, and neither are invisible ones unless the searcher carries FLAG_TARGETS_INVISIBLE.
  • get_targeters() returns a snapshot. Packed arrays copy on write, so editing the result changes nothing on the server and later changes never show up in it.
  • Search only ever visits a candidate through its center chunk. Reading G_ChunkingServer._entityCenterColumn/_entityCenterRow instead of the coverage rectangle is what makes a multi-chunk entity scored exactly once.

Verification

The link graph was fuzz-tested against its invariants: 40 worlds × 400 random assign, drop, hide, announce, remove and release operations, asserting that every back reference resolves, every targeter index matches its slot, nobody targets their own team or a removed entity, and that a reachable priority candidate is never passed over. All pass.

That validated the algorithm, ahead of the GDScript. The end-to-end suite in res://Tests/EndToEndTest.gd now drives search, approach, combat and flee through G_ChunkingServer and G_TargetingServer together inside Godot itself.
