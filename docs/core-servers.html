Core Servers

A_CoreServer is the abstract base of the three server autoloads. It owns every piece of entity data they share, and the one lifecycle that creates and removes entities. This page explains every one of its variables, with an example and a drawing each.

Five ideas that make the rest easy to read

1 · ids

An entity is an integer, not an object. register() hands out an entity id. Every property of that entity is one cell at that index in a packed array: _entityPosition[7] is where entity 7 stands, _entityTeam[7] is its team. No node, no object, no dictionary per entity.

2 · static

The data exists exactly once. Every array is a static var on A_CoreServer. The three autoloads extend it, so all three see the same arrays. A position written through G_ChunkingServer is read by G_HitServer in the same instant, without a call between them.

3 · prefix

The name says what indexes the array. _entity… is indexed by entity id, _slot… by membership slot, _chunk… by chunk id, _team… by team, _curve… by curve id. _teamChunk… and _teamColumn… are one flat array with one block per team.

4 · chains

Lists are chains of ids, not arrays of arrays. "Everyone in chunk 6" or "everyone targeting entity 0" is stored as a linked chain: a First… array holds the head, …Next and …Prev arrays hold the links. Adding or removing a member is a few integer writes and never copies a list.

5 · NO_ID

−1 means "points nowhere". One constant, NO_ID, ends every chain and marks every missing target, slot, chunk or curve. In the drawn arrays below it shows up faded.

Architecture

One base class, three autoloads, one copy of the data

A_CoreServer is an @abstract class that extends Node. It is never instantiated. G_ChunkingServer, G_HitServer and G_TargetingServer each extends A_CoreServer and are registered as autoloads in project.godot. They are three separate objects, but a static var belongs to the class, not to an object, so there is one copy of each array and all three servers read and write it.

What each server adds is its own queries (hit shapes, target search) and its own scratch data: temporary state for the query that is running, such as the candidate buffer of a hit or the best score of a search. Scratch data is a normal instance var on the one server that uses it, never on A_CoreServer.

The lifecycle is static too and is always called on the base class: A_CoreServer.register(…). It fills in the chunk, hit and targeting side of an entity in one call, so there is no way to have an entity that exists on one server but not on another.

One tick, in the order the calls belong

Entity ids

One id, four calls, three sides filled in at once

  1. 1

    register(position, radius, team, groups, moduleManager, hitProfile, targetingData) takes an id from _freeIds or appends a fresh cell to every per entity array. It then fills in the chunk side (team, groups, position, radius, chunk memberships, center chunk), the hit side (module manager, height band, hit groups, radius curve) and the targeting side (state SEARCH, groups, radii, flags). A null hit profile or targeting data falls back to a default without any groups: the entity is inert, but it still stands on the chunk index and can be targeted.

  2. 2

    pre_unregister(id) announces the removal: _isEntityPendingRemoval[id] = 1 and every targeter drops it. The entity keeps acting (moving, hitting, holding its own target), but it can no longer be hit or found by a search. Typical use: a death animation.

  3. 3

    unregister(id) removes it: it drops its own target, its remaining targeters drop it, it leaves every chunk and its center chain, and its id goes onto _removedIds. The id is now locked: it is not handed out again yet. A second unregister() of the same id does nothing.

  4. 4

    release_removed_ids(), once per tick and last, clears both flags, drops the module manager and the radius curve, and moves every locked id onto _freeIds. The next register() takes the id handed back last.

Why the lock? Say id 1 dies in the middle of a tick while a hit that already collected id 1 is still being dispatched. If id 1 were free at once, an entity spawned in between would get id 1 and take the damage meant for the dead one. Locked, the old id 1 is skipped by every query (they all check _isEntityPendingRemoval and _isEntityRemoved) until the tick is over.

Worked example: id 1 dies

# start: the example world. id 0 targets id 1; id 1 and id 2 target id 0. A_CoreServer.pre_unregister(1) # _isEntityPendingRemoval[1] = 1 # id 0 targeted id 1 → id 0 drops it: _entityTarget[0] = -1, state SEARCH A_CoreServer.unregister(1) # _isEntityRemoved[1] = 1 # id 1 drops its own target (id 0): chain of id 0 was 2 → 1, now 2 # slot 1 (id 1 in chunk 6) is unlinked → _freeSlots = [1] # defender count in chunk 6: 2 → 1, in column 2: 3 → 2 # defender groups in chunk 6: 0b11 → 0b10, column 2: 0b11 → 0b10, map: 0b11 → 0b10 # center chain of chunk 6 was 2 → 1, now 2; _removedIds = [1] A_CoreServer.release_removed_ids() # both flags back to 0, module manager dropped, _freeIds = [1] A_CoreServer.register(…) # returns 1 again: the id is reused, every side filled in fresh

Chunk index · which entity stands in which chunk, plus per team summaries

Two kinds of membership live here. A slot lists an entity in every chunk its radius touches: that is what a hit walks. A center lists it in one chunk, the one its position falls into: that is what a targeting search walks, so a large entity is scored once. On top sit per team counts and group masks at three levels (chunk, column, map), so a query can skip empty space without opening a chunk.

Overview: slots, centers and summaries in the example world — open this once before the rows below

Seven slots: id 0 in chunk 0, id 1 in chunk 6, id 2 in chunks 1, 2, 5 and 6, id 3 in chunk 11. Each slot sits in two chains at once: the chain of its chunk (who stands here?) and the chain of its entity (where does it stand?).

# Who stands in chunk 6? slot = _chunkFirstSlot[6] # 5 → _slotEntity[5] = id 2 slot = _slotChunkNext[5] # 1 → _slotEntity[1] = id 1 slot = _slotChunkNext[1] # −1 → done # Where does entity 2 stand? slot = _entityFirstSlot[2] # 5 → chunk 6, then 4 → chunk 5, 3 → chunk 2, 2 → chunk 1, then −1

Reference · every function of A_CoreServer

Functions

All functions are static. The four public ones are the lifecycle, called as A_CoreServer.register(…). The _ ones are internal to the servers: the three autoloads call some of them (for example G_ChunkingServer.set_position() calls _move_to_chunk_area()), the game never does.

Internal · lifecycle helpers

_reject_removed_id(p_id, p_callerName) → boolO(1)Guard for public setters

Returns true and pushes a warning such as G_ChunkingServer.set_position() got the removed entity 1, ignoring it. when the id is removed. set_position(), set_radius() and acquire_target() call it, because changing a removed entity would link it back into the chunk index or a targeter chain.

_acquire_id() → intO(1)Pops a free id or appends a fresh one

A fresh id is appended with neutral values: team 0, groups 0, EMPTY_CHUNK_AREA, every link NO_ID, state SEARCH. A reused id is returned as it was left by the release: out of every chunk and chain, so register() treats both alike. Returns _entityTeam.size() − 1 for a fresh id.

_register_chunk_side · _hit_side · _targeting_sideO(chunks)Fill in one side of an id

The three steps of register(), one per server. The chunk side also holds the entity core (team, groups, position, radius), because the chunk index needs team and groups to write its counts and masks. _pack_targeting_flags() turns the four booleans of an R_TargetingData into the flag byte.

_clear_target(p_id)O(1)Unlinks an entity from its target's targeter chain

Does nothing without a target. Otherwise unlinks p_id with its prev/next links, lowers the target's count, sets _entityTarget = NO_ID and the state to SEARCH.

_release_targeters(p_id, p_exemptFlags)O(targeters)Makes the targeters of an entity drop it

Walks the targeter chain (reading each next link before the entry is unlinked) and calls _clear_target() on every targeter whose flags share no bit with p_exemptFlags. Removal passes 0 (everyone drops it); turning invisible passes FLAG_CAN_TARGET_INVISIBLE, so targeters that see invisible entities keep it.

Internal · radius curves

_set_radius_curve(p_id, p_curve)O(1) or one bakeGives an entity a (shared) curve id

null releases the current curve. The same curve again does nothing. Otherwise releases the old curve, looks the new one up in _curveIdByCurve, acquires and bakes a new id only if it is unknown, and raises the user count. Note: a Curve edited after it was baked is not re-baked; the servers treat curves as fixed archetype data.

_acquire_curve_id(p_curve) → intO(samples)Stores and bakes a new curve

Pops _freeCurveIds or appends (growing _curveRadiusFactors by 65), sets the user count to 0, registers the curve in the dictionary and calls _bake_radius_factors().

_bake_radius_factors(p_curveId, p_curve)O(samples)Samples a curve into 65 factors from 0 to 1

Asserts max_value > 0. Sample i is taken at min_domain + i / 64 * (max_domain − min_domain), divided by max_value and clamped to 0–1. So any authored domain and value range works: Godot's default 0–1 curve as well as a curve authored in world units.

tail curve, domain 0 … 1, value 0.25 … 1.0, max_value 1.0 sample 0 at 0.0 → 0.25 / 1.0 = 0.250 sample 32 at 0.5 → 0.625 sample 64 at 1.0 → 1.000
_release_curve(p_id)O(1)Drops an entity's curve, frees unused ids

Sets the entity's curve id to NO_ID and lowers the user count; at 0 it erases the dictionary entry, nulls _curveById and pushes the id onto _freeCurveIds.

Internal · chunk index upkeep

_compute_chunk_area(min, max) · _compute_circle_chunk_area(center, r)O(1)World rectangle → chunk area, clamped to the map

Floors both corners to columns and rows and clamps them into the grid. The circle variant builds the bounding square center ± radius first; entities, circle hits and sector hits use it.

_move_to_chunk_area(p_id, p_area)O(changed chunks)Moves an entity onto a new chunk area, touching only the difference

Returns at once when the area is unchanged. Otherwise walks the entity's slot chain and removes every slot whose chunk is outside the new area, then adds a slot for every chunk of the new area outside the old one. EMPTY_CHUNK_AREA on either side makes it "add all" or "remove all".

_update_center_chunk(p_id, p_position) · _unlink_center(p_id)O(1)Keeps the one center membership current

Computes the chunk the position falls into; returns if unchanged. Otherwise unlinks the entity from its old center chain (via the prev/next links) and pushes it at the head of the new one, updating the cached column and row.

_add_membership(p_id, p_chunkId) · _acquire_slot()O(1)One more "entity stands in chunk"

Takes a slot, pushes it at the head of the chunk's chain and of the entity's chain, adds 1 to the counts, and merges the entity's groups upwards: chunk, then column only if the chunk mask changed, then map only if the column mask changed.

_remove_membership(p_slot)O(1) + rebuildsOne "entity stands in chunk" less

Unlinks the slot from both chains (a fixed number of writes), frees it, subtracts 1 from the counts and rebuilds the masks upwards while they change. A bit can't simply be cleared, because another entity may still carry it; so each level is re-ORed from the level below, and every rebuild stops once its running OR reaches the old value again: the mask can only shrink, so a match means nothing changed.

_change_membership_counts(chunk, team, delta)O(1), rarely O(columns)Writes ±1 through chunk and column, keeps the span

Adds delta to the chunk and the column count. When a column count goes 0 → 1, _extend_team_column_span() widens the span if needed. When it goes 1 → 0, _shrink_team_column_span() runs: a one-column span empties the team (both ends NO_ID); otherwise, only if the emptied column was an end, it scans inwards to the next column with a count.

_merge_groups_into_* · _rebuild_*_groupsO(1) · O(level below)The three levels of the mask cascade

_merge_groups_into_chunk/_column return whether the mask changed; _merge_groups_into_map is the last step. _rebuild_chunk_groups walks the chunk's slot chain for the team's entities; _rebuild_column_groups ORs the CHUNK_ROWS chunk masks of one column; _rebuild_map_groups ORs the CHUNK_COLUMNS column masks. All three rebuilds stop early at the old value.

Contract

What callers have to respect

  • Call the lifecycle on the base: A_CoreServer.register(…), never through an autoload.
  • Treat every shared array as read only. Write through the lifecycle and the set_… functions of the servers; writing _entityPosition directly leaves the chunk index describing the old position.
  • release_removed_ids() once per tick, after everything else. It is the only thing that recycles ids; the lock it releases keeps late hits away from new entities.
  • A removed id is dead until register() hands it out again. Most getters do not check; set_position(), set_radius() and acquire_target() ignore it with a warning.
  • Team and entity groups are fixed per registration. There is no setter; the counts and masks they were written into could not follow.
  • Up to 64 entity groups and 64 hit groups. Both are bits in an int; the game defines their meaning.
  • Radius curves are archetype data. Share one Curve per archetype; edit it before the first entity uses it.
  • The grid is fixed on class load. Changing the map size or chunk counts means changing C_ChunkingServer and restarting.
